# 우연한 식탁 (Wooyeon Table)

매주 목요일 저녁, 처음 보는 사람들과 함께하는 소셜 다이닝 서비스의 MVP입니다.
**신청 → 결제 → 자동 매칭 → 식당·단체방 안내 → 식사 → 피드백 → 다음 매칭**을 하나의 흐름으로 잇고,
정상 흐름은 운영자 개입 없이 끝나며 운영자는 자동 처리가 안 된 **예외만** 봅니다.

2026 우연한식탁 MVP 개발 해커톤 출품작입니다.

- **배포 주소:** https://social-dining-mvp.vercel.app
  - 참가자 앱: `/` → [데모 시작하기]
  - 운영자 어드민: `/admin`

## 3분 데모

1. 첫 화면에서 **[데모 시작하기]** → 나만의 데모 회차(10/22 목, 홍대·강남, 가상 참가자 23명)가 만들어집니다. 다른 방문자의 데모와 섞이지 않습니다.
2. 프로필·선호를 확인하고 저장합니다. 미리 채워져 있으며, 바꾸면 매칭 결과도 달라집니다.
3. **신청 화면**에서 날짜·지역(다른 지역 재배치 후보 포함)과 이용권을 고르고 **모의 결제**합니다. (완료 조건 1)
4. 화면 위 **데모 바(가상 시계)**의 버튼을 차례로 누릅니다. 단계마다 실제 자동화 코드가 실행됩니다. 실제 서비스라면 스케줄러가 이 시각에 같은 코드를 실행하고, 데모에서는 가상 시계 버튼이 그 역할을 대신합니다.

| 데모 바 | 일어나는 일 | PRD 완료 조건 |
|---|---|---|
| 매칭 마감 시각으로 이동 | 자동 매칭 → 재배치 → 자동 확정 → 식당 배정 → 단체방·알림 발송 | 2~7 |
| 모임 하루 전으로 이동 | D-1 리마인드, "참석할게요" | 9 |
| 식사 시작 | 단체방에서 직접 **체크인**, 대화 카드 3장(첫 장은 테이블 공통 관심사로 생성) | 9·10 |
| 식사 종료 | 피드백 요청 → 전체 만족도, 분위기·대화·식당 점수, 재참여·추천 의향, 사람별 선호, 신고 | 10 |
| 다음 회차 매칭 실행 | 피드백이 반영된 다음 주 매칭 + **반영 전후 비교** | 11 |

5. 데모 바의 **[실패 참가자 보기]** → 매칭 실패 사유와 일정 이동·이용권 보관·환불 선택 (완료 조건 8)
6. **[운영자 화면]** → 예외 처리함의 식당 부족 1건만 처리하면 정상 흐름으로 돌아갑니다 (완료 조건 12)

[처음부터]를 누르면 데모가 초기화됩니다. 제출용 테스트 계정(참가자 / 매칭 실패 참가자 / 운영자)은 제출 안내에 따로 적었습니다.

## 자동 매칭 규칙

| 구분 | 내용 |
|---|---|
| **필수 조건** (하나라도 어기면 확정 불가) | 결제 완료, 같은 날짜·지역, 4~6명, 나이 차 8살 이내, 차단·신고·비선호 관계 없음 |
| **선호 점수** (0~100, 어드민에서 가중치 조정) | 성비 30 · MBTI 20 · 공통 관심사 20 · 원하는 상대 성향 15 · 새로운 사람 비율 15, 서로 "또 만나요" 쌍은 가산 |
| **자동 확정** | 최소 점수(기본 60) 이상이면 운영자 승인 없이 확정 |
| **재배치** | 같은 회차 빈자리 → 신청자가 고른 다른 후보 일정 → 실패 사유 기록 |
| **피드백 반영** | 함께 앉음 → "만난 적 있음"(새로운 사람 점수 감점), 서로 "또 만나요" → 가산, "다시 안 만날래요" → 같은 테이블 금지 |
| **설명 가능성** | 테이블마다 "함께하게 된 이유" 문장과 참가자별 이유를 생성해 참가자·운영자에게 보여줌 |

- 단위 테스트 9개 (`npm test`): 필수 조건, 차단 쌍 분리, 실패 사유, 재배치, 같은 입력 같은 결과 등
- 가상데이터 294명의 지난 회차 재매칭: 평균 테이블 점수 78.2 → 82.0, 최소 점수 미달 테이블 4 → 0
- 2주 연속 시뮬레이션: "다시 안 만날래요" 쌍 분리 4/4, 2주차 전원 배정 4/4

## 보안 설계

보안을 1순위로 두었습니다. 원칙은 **"인증은 검증된 서비스에 맡기고, 권한은 DB와 서버에서 두 번 막는다"**입니다.

- **인증:** Supabase Auth를 씁니다. 비밀번호 저장·세션 관리를 직접 만들지 않았습니다. 심사위원은 [데모 시작] 시 비밀번호 없는 익명 계정을 받고, 제출용 테스트 계정 3개는 서버에서 무작위 비밀번호로 만들었습니다. 회원가입 화면은 없습니다.
- **DB 권한(RLS):** 모든 테이블에 RLS를 켜고 기본값은 전부 거부입니다. 비로그인(anon)에는 어떤 권한도 없고, 로그인 사용자도 **자기 샌드박스만 읽기**가 가능합니다. 판단 기준은 브라우저가 보낸 값이 아니라 서명 검증된 `auth.uid()`입니다.
- **쓰기:** 결제·매칭·환불·피드백 등 모든 쓰기는 서버에서 입력값과 소유 관계를 검증한 뒤 관리자 키로 실행합니다. 관리자 키는 `server-only`로 브라우저 번들에 들어가지 않습니다.
- **세션 쿠키 httpOnly:** 브라우저 스크립트가 로그인 정보를 읽을 수 없어 XSS로 세션을 훔칠 수 없습니다.
- **보안 헤더:** CSP, X-Frame-Options: DENY, X-Content-Type-Options, Referrer-Policy, Permissions-Policy. 아이콘도 외부 스크립트 없이 인라인 SVG로 넣었습니다.
- **기타:** 로그인 실패 메시지 통일(계정 존재 여부 비노출), 앱 내부 경로로만 이동(오픈 리다이렉트 차단), 주요 상태 변경(신청·결제, 매칭, 실패 처리, 예외 처리, 규칙 변경, 가상 시계) 감사 기록, 방문자별 샌드박스로 피해 범위 격리.
- **점검:** Supabase Security Advisor로 점검해 경고를 수정했고, 남은 경고 2종(익명 사용자 정책 = 의도한 설계, 유출 비밀번호 차단 = 유료 플랜 전용)은 근거와 함께 수용했습니다. 실제 요청으로 비로그인 차단, 타인 데이터 조회·수정 불가를 확인했습니다.
- **데이터:** 실제 개인정보는 쓰지 않습니다. 주최측 설문 원본과 정제본은 저장소에 올리지 않고, 연락처·인스타 ID 컬럼은 읽지도 않습니다.

## 구조

| 경로 | 역할 |
|---|---|
| `src/lib/matching/engine.ts` | 매칭 엔진 (DB와 분리된 순수 함수, 테스트 대상) |
| `src/lib/matching/run.ts` | 매칭 실행·저장, 같은 회차 재실행 시 중복 방지(idempotency) |
| `src/lib/automation/meetup.ts` | 식당 배정·재시도·예외 등록, 단체방·알림, 리마인드, 대화 카드, 피드백 요청 (중복 발송 방지 키) |
| `src/lib/feedback/loop.ts` | 피드백 저장, 관계(만남·상호 호감·비선호) 기록, 반영 전후 비교 |
| `src/lib/demo/` | 방문자별 샌드박스 생성, 가상 시계 단계 |
| `src/app/app/` | 참가자 모바일 웹앱 |
| `src/app/admin/` | 운영자 어드민 (대시보드·예외 처리함·피드백 요약, 매칭 모니터, 신청자·결제·참석, 규칙, 자동 처리 기록) |
| `supabase/migrations/` | 테이블 21개 + RLS |
| `scripts/` | 가상데이터 정제·적재, 매칭 비교, 테스트 계정 생성 |

상태값은 PRD 12장대로 **신청·결제·매칭·참석 4개를 분리**했습니다.

## 기술 스택
Next.js 16 (App Router, Server Actions) · TypeScript · Tailwind CSS 4 · Supabase (Postgres, Auth, RLS) · Vercel (서울 리전)

## 로컬 실행
```bash
npm install
cp .env.example .env.local        # Supabase 값 입력
npm run dev
npm test                          # 매칭 엔진 테스트
```

가상데이터 적재 (원본은 주최측 소유라 저장소에 없음)
```bash
python3 scripts/clean_virtual_data.py <가상데이터.xlsx 경로>   # data/private/에 정제본 (git 제외)
node --env-file=.env.local scripts/seed-base.mjs                # base 샌드박스에 적재, 다시 실행해도 같은 결과
```

## 개발 방식 (AI 활용과 직접 판단)

AI 코딩 도구(Claude Code)를 활용해 7일 안에 기획부터 배포까지 진행했습니다. 무엇을 AI로 빠르게 했고, 어떤 판단을 직접 했는지 구분해 기록합니다.

| 구분 | 내용 |
|---|---|
| AI 활용 | 자료 요약·데이터 분석, 코드 작성, 단위·브라우저 자동 테스트, 문제 원인 추적 |
| 직접 판단 | 범위와 우선순위(배점 순), 운영 정책 8개, 필수/선호 조건 구분, 성비를 선호 조건으로 둔 결정, **보안 1순위 로그인 방식**, 디자인 시안 확정, 지난 날짜를 매칭 이력으로 쓰는 데이터 방향 |

작업 기록은 Blaybus Workspace에, 변경 이력은 PR 단위로 남겼습니다.
